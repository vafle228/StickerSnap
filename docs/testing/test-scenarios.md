# StickerSnap — тестовые сценарии

Что и на каком уровне проверяем, зачем это нужно и что уже написано. Документ живой: новый экран
или эндпоинт приходит вместе со своими строками в таблицах ниже.

Статусы в таблицах:

- ✅ — тест есть в `main`;
- 🆕 — тест добавлен вместе с этим документом;
- ○ — код есть, теста пока нет: писать следующим;
- ⏸ — кода ещё нет (сервер, рендер, Electron), тест пишется вместе с ним.

## 1. Где мы сейчас

На 11 октября 2026 в репозитории есть SPA (этап 1a: редактор, «Проекты», «Настройки», демо-сервер
на MSW) и пустой ASP.NET-сервер на 16 строк, который только раздаёт SPA. До этого PR было 13 файлов
и 87 юнит-тестов, все — чистая логика без DOM: математика таймлайна, кропа и кадра, форматирование,
реестр горячих клавиш, тосты, живые обновления через хаб.

Чего не было совсем:

- состояния редактора и команд таймлайна, которые меняют сцену (I/O, «+ Отрезок», удаление с «Вернуть»);
- проверки, что демо-данные ведут себя как контракт: экраны строятся на `?mock`, и если демо-сервер
  отвечает не так, как будет отвечать настоящий, это всплывёт только на интеграции;
- компонентных тестов (ни jsdom, ни Testing Library не подключены);
- e2e-сценариев в браузере;
- любых тестов сервера и рендера: их кода ещё нет.

Этот PR закрывает первые два пункта (+7 файлов, +48 тестов, всего 135) и описывает остальные.

## 2. Уровни и инструменты

| Уровень      | Что проверяет                                                      | Инструмент                                    | Где лежит                                | В CI                            |
| ------------ | ------------------------------------------------------------------ | --------------------------------------------- | ---------------------------------------- | ------------------------------- |
| Юнит         | Чистая логика: математика, сторы, команды, форматирование          | Vitest, среда node                            | `src/web/src/**/*.test.ts` рядом с кодом | `npm test`                      |
| Контракт     | Схема и демо-сервер совпадают с `openapi.yaml`                     | `check:api`, Vitest + `msw/node`              | `src/web/src/mocks/*.test.ts`            | `npm run check:api`, `npm test` |
| Компонентный | Экран или карточка реагирует на клики и клавиши как в артборде     | Vitest + jsdom + Testing Library (подключить) | `*.test.tsx` рядом с компонентом         | `npm test`                      |
| E2E (SPA)    | Пользовательский путь целиком в настоящем браузере                 | Playwright против `vite` с `?mock=<сценарий>` | `src/web/e2e/*.spec.ts`                  | отдельный job                   |
| Сервер       | Эндпоинты, ошибки Problem Details, проект как файл                 | xUnit + `WebApplicationFactory`               | `tests/StickerSnap.Server.Tests`         | `dotnet test`                   |
| Рендер       | Сцена → filtergraph; корпус роликов → валидный .webm ≤ 256 KB      | xUnit, FFmpeg из закреплённой сборки          | `tests/StickerSnap.Render.Tests`         | отдельный job, по метке         |
| Десктоп      | Electron поднимает сервер, передаёт порт и токен, окно открывается | Playwright `_electron`                        | `src/desktop/e2e`                        | на Windows и Linux              |

Правила для всех уровней:

- Имя теста — поведение, которое видит пользователь, а не имя функции: «stops O at 3,00 s and shows
  the hint», а не «moveEdge returns limited». Так тесты читаются как спецификация артбордов.
- Тесты на TypeScript strict, как весь клиент; `!` запрещён линтером, поэтому сужаем типы явно.
- Тест не пропускают и не ослабляют, чтобы CI позеленел. Падает — чиним код или меняем тест вместе с
  решением, которое поменяло поведение (решение — в плане или контракте).
- Демо-данные — строго по контракту, как и код. Новое поле в моке — сначала правка в документе
  «StickerSnap — API-контракт».
- Юнит-тесты не трогают сеть и таймеры по-настоящему: `vi.useFakeTimers()`, `msw/node`.

## 4. Контракт: схема и демо-сервер

Экраны этапа 1a строятся на демо-данных, а сервер пишется позже. Цена расхождения — переделка
экранов на интеграции, поэтому демо-сервер проверяется так же строго, как будет проверяться настоящий.

| Сценарий                                                                                         | Что защищает                                                       | Статус                       |
| ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------ | ---------------------------- |
| `schema.d.ts` сгенерирован из текущего `openapi.yaml` и компилируется в strict                   | Типы клиента не отстают от контракта                               | ✅ CI `check:api`            |
| Обработчики MSW типизированы по схеме: путь, тело и ответ из контракта                           | Демо-данные не придумывают поля                                    | ✅ сборка (`mocks/route.ts`) |
| HTTP-статус каждого кода ошибки совпадает с таблицей `ErrorCode` в контракте                     | Мок 409 там, где сервер ответит 422, ломает ветку обработки ошибки | 🆕 `mocks/route.test.ts`     |
| Демо-сервер через тот же типизированный клиент, что и экраны (`mocks/handlers.test.ts`):         |                                                                    | 🆕                           |

| — «Убрать из списка» → «Вернуть» по пути; удалённый в корзину не возвращается                    | R21: убрать без удаления файла                                     | 🆕                           |

запускать его и против MSW, и против `WebApplicationFactory`. Тогда расхождение мока и сервера
ловится на CI, а не на ручной проверке.

## 6. E2E в браузере (Playwright)

Несколько длинных путей пользователя по настоящему DOM и CSS. Запускаются против `vite` с демо-данными:
`/?mock=<сценарий>` даёт детерминированное состояние без сервера. Каждый сценарий — путь, который

## 10. Порядок работ

1. ✅ Этот PR: юнит-тесты стора и команд редактора, контракт демо-сервера.
2. Подключить jsdom и Testing Library, покрыть `useProjectActions`, слои окон и оптимистичные настройки
   (раздел 5).
3. Undo/redo и автосохранение — писать сразу с тестами из 3.7: это самые дорогие баги для пользователя.
4. Playwright: три первых пути из раздела 6 (первый запуск, отрезок, «Проекты») и job в CI.
5. Сервер: тестовый проект и `dotnet test` в CI вместе с первыми эндпоинтами; общий набор
   контрактных сценариев для мока и сервера.
6. Компилятор сцены и корпус рендера — вместе с рендер-пайплайном этапа 1.

## 11. Как запускать

```bash
npm test                      # все юнит- и контрактные тесты SPA (Vitest)
npm test -- timeline          # только файлы, где в пути есть «timeline»
cd src/web && npx vitest       # в режиме наблюдения при разработке
npm run check:api             # схема совпадает с openapi.yaml
```
