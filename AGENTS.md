# StickerSnap — инструкции для разработки

Инструкции действуют на весь репозиторий. Сверено с кодом и CI 12 ноября 2026 года.
Новые решения пользователя имеют приоритет. Документацию и задачи ведём на русском;
имена типов, функций и файлов — на английском.

## Продукт и границы

StickerSnap превращает видео и GIF/WEBP в видеостикеры и custom emoji для Telegram.
Пользователь открывает файл или видео по ссылке YouTube/Giphy, меняет отрезки, кадрирование, масштаб,
скорость и повтор, смотрит точное превью, экспортирует WEBM и публикует результат в пак.
Проекты сохраняются в `.ssproj`; редактор поддерживает undo/redo и автосохранение.
Есть список проектов, проверка WEBM, управление/копирование паков, привязка Telegram,
настройки и отправка отзывов/диагностики.

Основной продукт — Electron: Windows/Linux x64, macOS arm64 и x64.
Браузерный запуск нужен для разработки и проверки SPA с тем же локальным API.
Telegram Mini App показывает паки/стикеры, управляет связанными компьютерами,
подтверждает привязку и принимает отзывы. Полного редактора в Mini App нет.

```text
Electron → React SPA → локальный ASP.NET Core → FFmpeg / файлы проектов
                                ↓ HTTPS
                     Python bot-service → Telegram Bot API
                                ↑ HTTPS
                       Telegram Mini App
```

Токен Telegram-бота принадлежит только Python-сервису. Electron и .NET публикуют через
облачный API с ключом устройства, без прямых вызовов Bot API. Видео обрабатывается локально.
Экспорт OpenTelemetry в desktop-режиме отключён; диагностика для отзыва отправляется
отдельным действием пользователя.

## Архитектура и стиль кода

### Общие правила

- Сохранять архитектуру и местный стиль модуля. Предпочитать короткий прямой код,
  guard clauses и простые выражения вместо лишней вложенности. Не вводить абстракции
  без конкретного потребителя или существующей границы между слоями.
- Доменная логика находится в модели/сценариях. UI, HTTP-контроллер и Telegram handler
  преобразуют ввод и вызывают сценарий. Чистые вычисления отделены от I/O.
- Время, сеть, диск и процессы подставляются через существующие порты; тесты управляют
  временем и подменяют внешние адаптеры. Не дублировать готовые механизмы ошибок и уведомлений.
- Не скрывать ошибки пустым `catch`, ложным успехом или бесконечным повтором.
  Обрабатывать ожидаемый сбой на подходящей границе, сохранять код ошибки и отмену.
- Технические комментарии обычно английские: объясняют причину, контракт, единицу измерения
  или инвариант. Не пересказывают операторы. Пользовательские строки — русские, в словарях.
- Не выполнять массовое форматирование, переименование или обновление зависимостей
  вместе с несвязанной задачей. Не отключать анализаторы и не ослаблять тест ради CI.
- Секреты, абсолютные пользовательские пути и приватную диагностику не включать
  в исходники, фикстуры, логи, коммиты и документацию.

### TypeScript / React

Стек: React 18, TypeScript strict, Vite, Zustand, TanStack Query, CSS Modules.
Зависимости фиксирует корневой `package-lock.json`; React Router в клиентах нет.

- Компоненты — именованные функции/exports, `PascalCase.tsx`; хуки — `use*`, утилиты —
  `camelCase.ts`. Props типизированы явно, type-only импорты — `import type`.
- Соблюдать `strict`, `noUncheckedIndexedAccess`, unused-проверки и ESLint strict.
  Сужать `undefined` явно; не применять non-null assertion `!` или `any` для обхода типов.
  Type assertion допустим на обоснованной границе адаптера, не вместо проверки входных данных.
- Prettier: двойные кавычки, trailing commas, ширина 100; настройки в
  [.prettierrc.json](.prettierrc.json). Generated-файлы форматирует их генератор.
- Zustand — локальное состояние UI/редактора, TanStack Query — серверные данные.
  Переиспользовать query keys и клиент `api`/`call()` из `shared/api`; не дублировать DTO
  и raw fetch по экранам. Оптимистическое изменение откатывается при ошибке.
- Сцена редактируется через `useEditor.edit()` / `editSegment()` в
  `features/editor/model/store.ts`: прямая запись обходит историю и автосохранение.
- Кнопка и hotkey вызывают одну команду. Математика кадра/crop/timeline находится в
  `model`, независимо от React/DOM. Эффекты идут в actions/hooks, не прячутся в JSX.
- Автосохранение сериализовано, с задержкой 1 с; export/publish ждут `flushSave()` и
  используют сохранённую revision. `revision_conflict` автоматически не повторять.
- Системные диалоги/файлы доступны через `shared/platform/Platform`.
  Экраны не импортируют Node/Electron и не дублируют ветвление браузер/desktop.
- UI использует `@stickersnap/ds`, CSS variables и CSS Modules для раскладки.
  Строки SPA добавлять в `shared/strings/ru.ts`; ошибки — через существующий `notifyProblem`.
- SPA сохраняет редактор смонтированным при смене секций. В Mini App навигация —
  стек `src/app/nav.ts`, согласованный с Telegram BackButton и `startapp`.

Примеры: [Button.tsx](src/ds/src/components/Button.tsx),
[actions.ts](src/web/src/features/projects/actions.ts),
[store.ts](src/web/src/features/editor/model/store.ts).

### C# / .NET

Решение — [StickerSnap.slnx](src/server/StickerSnap.slnx). `net10.0`, nullable и
warnings-as-errors заданы в `Directory.Build.props`, NuGet-версии — `Directory.Packages.props`.
Стиль: file-scoped namespaces, `PascalCase` для типов/методов, `_camelCase` для private fields,
`sealed` для конкретных реализаций, immutable records/`with` для снимков, primary constructors
для DI, где они уместны. Не переписывать существующие constructors ради косметики.

- Зависимости направлены внутрь: `Application → Core`, `Infrastructure → Application/Core`.
  Api вызывает Application; Infrastructure подключается только в `Api/Program.cs`.
- Core не знает внешние слои/фреймворки. Core/Application не зависят от `System.Net.Http`
  и не называют FFmpeg/ffprobe/yt-dlp в типах/namespace: движки скрыты портами.
  Infrastructure не зависит от Api или ASP.NET.
- Каждый конкретный Application-класс `FooService` реализует собственный `IFooService`.
  Внешние слои используют интерфейс. Регистрации — в существующих DI extensions.
- Async I/O имеет суффикс `Async` и передаёт `CancellationToken` по цепочке.
  Не блокировать `.Result`/`.Wait()`. Время для бизнес-логики/тестов — через `TimeProvider`.
- Контроллеры тонкие: DTO → интерфейс сервиса → DTO/HTTP. Ошибки идут через
  `AppException`/`ErrorCode` и Problem Details; русские формулировки остаются в клиенте.
- Сохранять существующую сериализацию read-modify-write: per-project locks,
  `SemaphoreSlim` с освобождением в `finally`, файловые записи через `AtomicFile`.
- `.ssproj` — версионированный JSON. Изменение схемы требует миграции и проверки старого
  файла; неизвестную более новую схему не перезаписывать с потерей данных.
- Ограничения проверяет [LayerTests.cs](src/server/StickerSnap.Tests/Architecture/LayerTests.cs).

Примеры: [SettingsService.cs](src/server/StickerSnap.Application/Settings/SettingsService.cs),
[SettingsController.cs](src/server/StickerSnap.Api/Controllers/SettingsController.cs).

### Python / bot-service

Python 3.13, aiogram 3 и FastAPI в одном процессе; зависимости — `uv.lock`.
Инструменты настроены в [pyproject.toml](src/telegram/bot/pyproject.toml).

- `domain` — чистые правила, frozen dataclasses, `StrEnum`; переходы возвращают новый объект.
  `application` — сценарии/порты `Protocol`; `infrastructure` — реализации;
  `api` — входные адаптеры. `main.py` — единственный composition root.
- `api` и `infrastructure` не импортируют друг друга. Правила проверяет `lint-imports`,
  типы — strict mypy, код/импорты — Ruff. Форматирование Ruff, ширина 100.
- `snake_case` для функций/переменных/модулей, `PascalCase` для классов, `UPPER_SNAKE_CASE`
  для констант. Полные аннотации, `T | None`, builtin generics, `collections.abc`.
- Async I/O, `Clock` и aware UTC вместо реальных часов в сценариях. SQL и Telegram
  скрыты портами. Связанные записи выполняются в одном async UnitOfWork с явным `commit`;
  выход без commit откатывает транзакцию.
- HTTP-модели наследуют `api/bodies.py:Body`: snake_case внутри, camelCase по сети.
  Валидация Pydantic не заменяет доменные инварианты.
- Таблицы — `infrastructure/database/tables.py`, миграции — соседний `migrations/versions`.
  После изменения модели создать и проверить Alembic-миграцию; при старте сервис делает upgrade head.
- Пользователь определяется проверенной авторизацией. Владение паком проверяется реестром
  сервиса; имя пака и user ID из запроса не доказывают право изменения.

Примеры: [linking.py](src/telegram/bot/src/stickersnap_bot/application/linking.py),
[persistence.py](src/telegram/bot/src/stickersnap_bot/application/persistence.py).

## API, данные и ограничения

Локальный API — `/api/v1`, облачный — `/v1`. JSON: camelCase, строковые enum,
UTC ISO 8601, размеры в байтах; отсутствующее optional-поле не заменяется `null`.
Границы отрезков — номера кадров источника, In/Out включительно, не секунды.
Ошибки — RFC 9457 Problem Details с `code` и параметрами; текст UI формирует клиент.

SignalR `/hubs/events` только отправляет события — полные снимки jobs/projects/account и др.
Команды идут REST. Клиент обновляет Query cache, после reconnect перечитывает состояние,
при недоступном hub временно опрашивает активные jobs. Не заменять события постоянным polling.
В сервере preview имеет отдельную последовательную очередь, export/publish делят другую.
Загрузки по ссылке имеют отдельную очередь и событие `downloadUpdated`.
Импорт существующего пака и создание копии — разные операции; подробнее об импорте,
копировании и ограничениях — в [DEVELOPMENT](docs/DEVELOPMENT.md#импорт-по-ссылке-и-копирование-паков).

Текущие значения приложения заданы в
[TelegramLimits.cs](src/server/StickerSnap.Core/Telegram/TelegramLimits.cs): WEBM VP9 без звука,
262144 байта, до 30 FPS, обычная длительность до 3 с; sticker с большей стороной 512,
emoji 100×100; ёмкость пака 120/200 соответственно. Экспериментальный long sticker до 10 с
с изменённой длительностью заголовка — отдельный режим с предупреждением, не официальная
гарантия Telegram. Изменение лимитов требует согласования контракта, валидатора, рендера и UI;
проверку Telegram описывать отдельно. Сцена сейчас содержит один video layer,
скорость 0,25–4, crop в целых пикселях внутри исходника.

При изменении API:

1. Изменить YAML: схемы, ошибки, операции и при необходимости `x-events`.
2. Согласованно изменить DTO/use case, адаптеры, клиент и MSW-фикстуры.
3. Выполнить `npm run gen:api`, `npm run check:api`, `npm run typecheck:api`.
4. Проверить контракты обеих затронутых сторон и реальный интеграционный путь.
   Ломающее локальный API изменение оформлять новой версией рядом с прежней, не менять молча `/api/v1`.

Generated-файлы руками не редактировать:

| Источник | Результат | Команда |
| --- | --- | --- |
| `src/contract/openapi.yaml` | `src/web/src/shared/api/schema.d.ts`, `events.ts` | `npm run gen:api` |
| `src/contract/bot-service.yaml` | `src/telegram/miniapp/src/api/schema.d.ts` | `npm run gen:api` |
| `src/ds/src/tokens.json` | `src/ds/src/tokens.css` | `npm run gen:tokens` |
| DS и standalone-витрина | `docs/design-system.html` | `npm run build:design-system` |

## Дизайн-система

Источники: [tokens.json](src/ds/src/tokens.json), [components.css](src/ds/src/components.css),
[components](src/ds/src/components), [motion.css](src/ds/src/motion.css),
[icons](src/ds/src/icons/paths.ts). HTML показывает эти исходники и правила применения;
не создавать независимую копию компонентов.

- Manrope и JetBrains Mono поставляются локально в `src/ds/fonts`.
- Две темы `light`/`dark`, пять акцентов `indigo`, `violet`, `raspberry`, `teal`, `graphite`.
  Использовать `data-theme` и `ss-accent-*`. Telegram выбирает тему, палитра остаётся StickerSnap.
- Перед новым контролом проверить существующие компоненты и варианты. Цвета, размеры,
  радиусы, тени и движение брать из DS, не создавать параллельную библиотеку внутри feature.
- Primary — главное действие, prism — публикация в Telegram, danger — необратимое действие
  в подтверждении. Disabled-контролу при необходимости дать объяснение, icon button — доступное имя.
- Сохранять управление клавиатурой, фокус, порядок слоёв, Esc и reduced motion.
  Проверять обе темы, все акценты и узкий экран; общая DS влияет на SPA и Mini App.
- После изменения токенов: `npm run gen:tokens`, `npm run check:tokens`.
  После изменения DS/примеров/правил пересобрать HTML и проверить в браузере, включая
  интерактивные контролы. В HTML не должно быть сетевых зависимостей, API и секретов.
- Dev-витрина: `npm run dev`, затем `http://127.0.0.1:5173/?showcase`.
  Она исключена из production SPA. Capture-скрипты и абсолютные `/@fs/` пути запрещены в сборках.

## Окружение и обязательные проверки

Полные команды запуска, конфигурация, матрица тестов и ограничения параллельного запуска:
[docs/DEVELOPMENT.md](docs/DEVELOPMENT.md). Читать перед запуском/проверкой затронутого компонента.

Node 24 из `.nvmrc`, .NET SDK 10, Python 3.13, uv; зависимости — `npm ci` и `uv sync --locked`.
FFmpeg/yt-dlp закреплены: `npm run fetch:ffmpeg`, `npm run fetch:ytdlp`.
Обычный dev: API на 5180 (`dotnet run --project src/server/StickerSnap.Api`), SPA на 5173
(`npm run dev`), Mini App на 5174 (`npm run dev:miniapp`), bot на 8080.

Проверять затронутые части: lint, typecheck, релевантные тесты и production build.
Корневые `npm test`, `lint`, `typecheck` покрывают только DS и web; desktop/Mini App — отдельно.
Серверные `Online`-тесты исключать явно: env opt-in нет, полный запуск обращается к сайтам.
Для влияющих на основной путь API/интеграционных изменений обязателен `npm run e2e:server`
с настоящим ASP.NET и FFmpeg. Для DS — пересборка HTML, `npm run build:design-system -- --check`
и проверка обеих тем/интерактивности в браузере. Для документации — факты, ссылки и команды.

Тесты проверяют поведение и контракты, не статическую разметку или копию реализации.
Для бага добавить воспроизводящий тест на нужном уровне. Сторы сбрасывать, временем управлять,
не использовать sleep вместо синхронизации. Mock-прогон не доказывает live-проверку Telegram.
Сбой окружения и непроверенную интеграцию явно указывать в результате.

## Процесс разработки

1. Прочитать AGENTS и TASKS, определить ожидаемое поведение и критерии готовности.
   Изучить нужные слои, контракты, дизайн и соседние тесты. Обычные задачи выполнять
   самостоятельно; крупные изменения архитектуры согласовывать. Уточнять недостающие решения.
2. Проверить `git status`, ветку и незакоммиченные файлы. Сохранить чужие изменения.
   Использовать подходящую ветку задачи; новую именовать `codex/<смысл-задачи>`.
   Не начинать feature в чужой ветке только потому, что она открыта. Worktree использовать
   при конфликте с текущей работой, не обязательно для каждого изменения.
3. В TASKS пометить задачу «В работе», записать проверяемые критерии. Новые крупные
   направления согласовывать; мелкие пункты внутри текущего запроса добавлять самостоятельно.
4. Реализовать связное изменение нужных слоёв. API менять начиная с YAML;
   DS — с обновлением исходников, примеров и HTML. Не оставлять временные обходы в production.
5. Выполнить проверки из матрицы, просмотреть diff, исключить лишние файлы, секреты,
   capture-вставки и несвязанные изменения. Сбой окружения отличать от падения теста.
6. Обновить документацию и TASKS: результат, проверки, ограничения/блокер.
   Ссылки на PR в TASKS необязательны. «Готово» означает выполнение критериев, не создание файла.
7. Делать **средние по объёму логические коммиты**: одна связная часть работы, пригодная
   для ревью и отката. Не дробить на каждую строку, не смешивать несвязанные задачи.
   Сообщение: конкретное название + пустая строка + описание, что сделано и зачем;
   значимые проверки/ограничения можно добавить в тело. Код, тесты и generated-результат
   сохранять согласованными. В staging добавлять только выбранные файлы.
8. Отправить ветку и создать PR в `main`, если пользователь не указал другую базу.
   Описать проблему, итоговое поведение и проверки. Дождаться CI на текущем commit,
   исправить относящиеся к задаче сбои, дождаться нового результата.
9. **Merge — только после согласия пользователя для текущего PR.** Зелёный CI не разрешает
   merge автоматически. Не включать auto-merge и не переносить согласие с другого PR.
   В завершении сообщить результат, проверки, ограничения и состояние PR/локальных изменений.

Это порядок будущей разработки; явное указание оставить работу локально или только
исследовать имеет приоритет. Не коммитить/пушить чужие изменения, не переписывать историю
и не делать force push без прямого запроса. Выпуск релиза не входит в обычную готовность задачи.

## CI, упаковка и релизы

Pipeline: проверки → сборка → быстрые тесты → Slow/E2E → `Pipeline passed`.
Перед merge нужен успех для последнего commit. Branch protection проверять отдельно;
dependency audit сейчас не блокирует gate. Команды упаковки, Build app, Deploy bot,
конфигурация VPS и observability описаны в [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md).

**Релизы выполняет пользователь.** Агент не запускает release workflow, не создаёт
теги и GitHub Releases. Production-деплой и изменения VPS — только по отдельному прямому
запросу. Разрешение на PR/merge не включает эти действия. Production-сборки не должны
содержать demo-данные, dev bar и capture-скрипты; `build:dev` для релиза не использовать.

## Поддержание инструкций

При изменении архитектуры, команд, генераторов или процесса обновлять этот файл в той же задаче.
TASKS хранит план и результаты, README — запуск/эксплуатацию, YAML — API,
исходники DS + HTML — дизайн. Не создавать конкурирующие списки задач и обязательные
внешние документы. Прошлый CI, mock-прогон и старая проверка Telegram не подтверждают
текущее состояние.
